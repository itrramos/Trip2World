# Internationalisation

Trip2World's interface is translatable. Adding a language is a JSON file and one line — no
component changes, no build changes.

---

## How it fits together

| | |
| --- | --- |
| `apps/web/messages/*.json` | The catalogues. One file per language |
| `apps/web/src/i18n/routing.ts` | Locale list, URL strategy, which languages are offered |
| `apps/web/src/i18n/request.ts` | Loads a catalogue per request and merges English underneath |
| `apps/web/src/i18n/navigation.ts` | Locale-aware `Link` and router |
| `apps/web/src/middleware.ts` | Detects the locale and rewrites the request |
| `app/[locale]/…` | Every page lives under the locale segment |

Built on [next-intl](https://next-intl.dev). The locale list is imported from
`packages/types`, not duplicated — the same list the API validates a profile's `locale`
against, so a language the UI cannot render can never be stored on an account.

---

## Three decisions worth knowing

**English has no URL prefix.** `/discover`, not `/en/discover`; only the other five carry
one. Trip2World was already deployed with those URLs live — in the PWA manifest's
`start_url`, in verification emails that have already been sent, and in whatever people
have bookmarked. A scheme that prefixed every locale would break all of them to benefit a
language nobody is using yet. This is `localePrefix: 'as-needed'`.

**English is merged underneath every other catalogue, key by key.** A translator can ship
forty per cent of a file and the page still renders real words — translated where they got
to, English everywhere else. The merge is recursive on purpose: a shallow spread would
replace an entire namespace the moment someone touched one string inside it, and every key
they had not reached yet would vanish.

**Only languages with a catalogue appear in the picker.** `routing.locales` has six
entries and all six *route* — `/de/discover` resolves and renders in English. But
`TRANSLATED_LOCALES` is what the switcher offers, because a menu entry that changes the URL
and nothing else looks broken.

## Adding a language

1. Copy `messages/en.json` to `messages/<code>.json` and translate the values.
2. Add the code to `TRANSLATED_LOCALES` in `src/i18n/routing.ts`.
3. Run `pnpm i18n:check`.

If the code is not already in `Locale` in `packages/types/src/enums.ts`, add it there
first — that list drives routing, static generation, and profile validation together.

### Rules for translators

- **Never translate anything inside `{braces}`.** `{name}` is an argument looked up by
  name. `{nome}` renders as the literal text `{nome}` to a real user.
- **Never translate tag names.** `<link>Terms</link>` — translate `Terms`, keep `<link>`.
- **Keep plural forms.** `{count, plural, one {# token} other {# tokens}}` uses the
  categories your language actually has; Portuguese needs `one`/`other`, Polish would need
  `one`/`few`/`many`/`other`.
- **`DELETE` is not a word.** In `settings.account.typeToConfirm`, the value arrives as an
  argument and is compared byte-for-byte by the API. Translate the sentence around it.

`pnpm i18n:check` enforces the first three. It fails on a key that does not exist in
English, a placeholder that was renamed or dropped, and a missing tag. Missing keys are
reported but do not fail — a partial catalogue is a legitimate state.

Portuguese was translated by an AI, not a native speaker. It is idiomatic European
Portuguese and consistent in register (informal `tu` throughout, matching the English
copy's tone), but **have a native speaker read it before you lean on it commercially.**
The failure mode is not incorrectness so much as phrasing that reads as translated.

## What is deliberately not translated

**The legal pages** — Terms, Privacy, Community Guidelines, Safety. They render in English
in every locale, with a notice explaining why. A mistranslated Privacy Policy is worse than
one you have to read in a second language, because it may not say what it appears to say,
and it is the English version that governs. These need a lawyer per jurisdiction, not a
translation pass. See `src/components/legal-page.tsx`.

**Country and interest names.** They come from `packages/shared` in English. They are
*sorted* in the reader's locale — `localeCompare(a, b, locale)`, so accented initials sort
correctly and "Deutschland" would file under D for a German reader — but the names
themselves are not localised. `Intl.DisplayNames` would handle countries properly and is a
reasonable next step.

**Currency.** Prices are formatted in the reader's locale — "€9.99" in English, "9,99 €" in
French — but the currency itself stays whatever the package is sold in. Converting it to
match the language would misrepresent what the card is charged.

**Server-authored text.** Validation messages and moderation reasons come from the API in
English. Where the server supplies a message it wins over the generic client-side copy,
because it is more specific. Localising the API's error catalogue is a separate piece of
work and is not done.
